## Glossary

| Term | Meaning here |
|---|---|
| **event** | one row; the only unit the collector knows about |
| **good / bad** | an event that passed schema validation vs one that failed; both are stored |
| **first touch** | the campaign values observed on a visitor's first ever visit, persisted in a cookie |
| **last touch** | the most recent non-empty campaign values observed, persisted in a cookie |
| **ingest date** | UTC date of `ingested_at`; the partition key. Not the event date |
| **instance id** | random id generated at collector boot; makes output filenames unique per container |
| **increment** | one shippable slice with its own spec file |
| **sink** | where events land, named by one URI; `file://`, `s3://`, `gs://` or `az://` |

| 2026-07-27 | **Collector validates but never rejects.** Always 2xx; valid → `data/events/dt=…`, invalid → `data/bad/dt=…` with the error list attached to the original payload.<br>*Why + alternatives rejected:* Snowplow's collector writes any payload to the raw stream regardless of validity and forks good from bad downstream in Enrich, which is what keeps that pipeline non-lossy. minuano has no Enrich stage, so the fork moves to collect. Rejected (a) validate-and-4xx — a snippet bug then silently destroys a day of traffic, which is anti-pattern #4 in `Personal/02-…/anti-patterns.md`; (b) no validation at all — truest to Snowplow, but leaves no feedback loop while the snippet is being written.<br>*Verified by:* Snowplow docs, "the Collector tries to write any payload to the raw stream, no matter its content, and no matter whether it is valid."<br>*Provenance:* web research 2026-07-27 (Snowplow fundamentals + failed-events docs); main thread, no sub-agent. |
| 2026-07-27 | **Partition raw by ingest date, not event date.**<br>*Why + alternatives rejected:* the collector must never reorganize a closed partition, and a client clock skewed by hours would otherwise write into a past day. Downstream pads ±1 day (ingestion-patterns Pattern 7, Boundary-File Padding). Rejected event-date partitioning: convenient for Athena, but makes raw mutable.<br>*Verified by:* `Personal/02-data-engineering-patterns/ingestion-patterns.md` §5, §7.<br>*Provenance:* main thread. |
| 2026-07-27 | **Nothing is derived from the request socket except `ingested_at`.**<br>*Why + alternatives rejected:* server-side GTM and future server SDKs relay on a visitor's behalf; deriving IP/user-agent/language from the socket would stamp every relayed event with the relay's identity, which is the standard failure mode of server-side tracking. | 2026-07-27 | **A new visitor's first event is tagged `first_touch`; every event after it is `last_touch`.**<br>*Why + alternatives rejected:* an event can carry only one `campaign` object, and the point of `campaign.attribution` is that first-touch never has to be reconstructed from event ordering. | 2026-07-28 | **`event_id` is minted by the client, and is optional forever in v0.**<br>*Why + alternatives rejected:* delivery is already at-least-once and already live. `sendBeacon`-then-`fetch` fallback, proxy retries, and the failed-flush-returns-to-buffer path in `writer.py` can each deliver one event twice, and until now a duplicate was undetectable and unremovable. An id cannot be added retroactively — every event collected before this exists without one, permanently — which is the same argument that justified capturing `gclid` off-plan. Rejected **making it required**: `schema/event.v0.json` is `additionalProperties: false` *and* would then reject every browser and GTM container still serving a cached snippet, turning working installs into `bad/` rows; optional costs nothing because a dedup that tolerates NULL is the same query. Rejected **a server-side id**: the collector would mint a fresh one per delivery, so the two copies of a retried event would get different ids — precisely the case the field exists for. Rejected **a natural key** (`anonymous_id` + `event_timestamp` + `path`): works today only because timestamps are millisecond-precision, and silently over-deduplicates real repeat events.<br>*What it does not do:* a GTM tag firing twice calls `build()` twice and mints two ids. That is a different defect and this deliberately does not mask it.<br>*Cost:* +36 bytes minified, +27 gzipped — `uid()` already existed in the snippet.<br>*Verified by:* `check_schema` 16 fixtures incl. `event_id_absent_is_valid` and `event_id_too_short`; `check_snippet` 22/22 incl. uniqueness across 5 events; the declared-column view in `sql/events.sql` reading **4,889 real production events that have no `event_id`** as NULL rather than failing to compile (the increment-4 declared-schema decision paying off).<br>*Provenance:* code review of `app.py`/`writer.py`/`minuano.js` 2026-07-28; main thread. |

| 2026-07-28 | **±1 day padding is downgraded from a correctness rule to a measured optimisation.** *Contradicts a previously written invariant — hence this entry.*<br>*What falsified it:* the 2026-07-27 decision log adopted Boundary-File Padding and both `CLAUDE.md` and `sql/events.sql` stated that downstream jobs "pad ±1 day", phrased as though a padded query were then correct. The first day of production data contained an event **166 days** behind its `ingested_at`. No fixed pad catches that, and since `event_timestamp` comes from a client clock on a public unauthenticated endpoint, it is attacker-controlled input in all but name — there is no upper bound available to pick.<br>*The replacement rule:* padding prunes files and loses a knowable fraction of rows; on day one ±1 day would have captured 99.96% of events. `health_clock_skew` measures that fraction per dataset, so the loss is visible rather than assumed. When completeness matters, scan without a `dt` filter or read a layer partitioned by `event_date`.<br>*Why + alternatives rejected:* **widening the pad** just moves the arbitrary number and still fails on the next outlier, while reading more files every query. **Clamping `event_timestamp` at collect** was rejected outright — it destroys the evidence of skew and violates the rule that `ingested_at` is the only server-derived field. **Partitioning raw by event date** makes raw mutable, which the append-only invariant exists to prevent; the right home for an event-date layout is the derived layer, which is increment 10.<br>*Verified by:* `health_clock_skew` on 4,889 real events — 4,864 within 5 minutes, 23 between 5 minutes and a day, 2 at -166.72 days.<br>*Provenance:* production data pulled from the live GCS sink 2026-07-28; main thread. |

| 2026-07-28 | **The derived layer is a separate prefix, not a compaction of raw in place.**<br>*Why + alternatives rejected:* three problems had no home — duplicate deliveries, untrustworthy client clocks, and ~1.9 events per object — and each one is a *transform*, which raw is forbidden to be. Rejected **compacting raw in place**: it directly violates the append-only invariant, and the moment a rewrite is possible a bug can destroy the only copy of collected data. Rejected **tuning `MINUANO_FLUSH_MAX_SECONDS`** to make bigger objects: traffic averages ~3.4 events/min, so useful file sizes need ~5 minutes of buffering, and the in-memory buffer is the one place an event exists in a single copy — buffer duration *is* loss exposure on a scale-to-zero platform. Rejected **an incremental job with a watermark**: a watermark needs a bound on lateness, which real traffic already falsified at 166 days; a full rebuild is correct and takes seconds at this volume, and the eventual fix is a windowed rebuild over `dt`, measured rather than guessed.<br>*The clock-trust rule:* `event_time_trusted` is a column, not a filter. Events whose `event_timestamp` differs from `ingested_at` by more than a day fall back to `ingested_at` for ordering and partitioning, and the original timestamp is preserved verbatim. This closes the backdating lever in `sessions.sql` (`error.md` TRAP-20) — a client could otherwise rewrite a whole session's attribution by claiming an impossible timestamp — **without** clamping at collect, which would destroy the evidence and blind `health_clock_skew`.<br>*Verified by:* `check_derived` 9/9, including that a NULL `event_id` is not collapsed (a `PARTITION BY` over NULL would delete 97% of current traffic) and that three consecutive rebuilds produce the same row count, not triple — the `OVERWRITE_OR_IGNORE` failure, in which the deduplication job silently becomes a duplication job. On real data: 10,572 events, 2,524 raw objects → 2 Parquet files, 4.0 MB NDJSON → 688 KB zstd.<br>*Provenance:* main thread, 2026-07-28. |

## Known gaps, deliberately accepted

| Gap | Why it is accepted, and when it stops being acceptable |
|---|---|
| **No consent gating on the first live install** | The first deployment is a *test* against one owned property, to prove the snippet works in a real browser. Deferred knowingly, not overlooked. It stops being acceptable the moment the tag is left running on a site with real visitors, or installed anywhere the owner is not the person who deployed it — first-party cookies plus URL and click-id capture is personal data under LGPD/GDPR. There is no cookieless mode in v0. |
| **No rate limit or write key** | `/collect` must be reachable by any browser, so it cannot be authenticated. Bounded for now by `--max-instances` and a bucket lifecycle rule. Revisit before any third party is given the URL. |
| **The snippet has never run in a real browser** | Closing this is the point of the first install. Cookie behaviour under Safari's ITP (a 7-day cap on script-written cookies) is the specific unknown, and no test in this repo can reach it. |

## Known deltas for schema v1

- **iOS attribution does not fit `campaign`.** Apple's AdServices returns an attribution *token*
  exchanged for numeric campaign/ad-group ids from Apple Search Ads — there is no `utm_source`.
  Android's Play Install Referrer *is* UTM-shaped and fits the current object unchanged.
- **`params` has no type discipline beyond scalar.** Fine for v0; a per-event-name parameter
  contract is the obvious v1 conversation.
